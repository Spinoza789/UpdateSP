name: Google Drive database backups
description: Production backup destination, lifecycle, and scheduling rules that prevent database and project-storage contention.

## Required backup format and transport

Backups must appear in Google Drive as one complete plain `.SQL` file, not a collection of parts. Initialize the authorized resumable upload through the existing connector, then send raw SQL chunks directly to the returned Google upload-session URL using Node's HTTPS client. Keep existing multipart backups and their restore compatibility.

**Why:** the user explicitly requested directly downloadable full SQL files. The observed partial-range failures are on the connector upload route, not a limitation of Google Drive's single-file uploads.

**How to apply:** never re-enable partial-range uploads through the connector proxy. Keep chunk sizes aligned to Google's 256 KiB requirement, interpret 308 as upload progress rather than following it as a redirect, validate the HTTPS Google upload destination, and keep the session URL server-side and out of logs because it grants upload access. After ambiguous writes, query acknowledged progress before resending. Verify the complete remote size/checksum before deleting local SQL; filename or size alone does not establish a valid backup. Complete SQL awaiting upload must not expire through age-based pruning, because a prolonged upload outage could otherwise delete the only complete local copy. Preserve existing copies, fail closed on same-name conflicts, and never prune Drive backups automatically.

## Scheduling and historical backup safety

Production database backups use `pg_dump --no-owner --no-privileges` and have the logical name `S&PBACKUP-YYYY-MM-DD_HH-MM-SS.SQL`. Historical multipart backups store numbered gzip objects and bounded manifest segments, with a root manifest committed last; restoration must reconstruct and hash-verify the exact SQL. Development servers do not run scheduled backups. Each production instance waits 10 minutes after startup, then attempts every 6 hours; a PostgreSQL advisory lock prevents simultaneous backups, and a locked-out attempt retries every 5 minutes until it runs. Each instance keeps at most one pending retry, so retries cannot fan out locally; concurrent instances may still produce an additional backup after the lock holder finishes. A complete SQL file whose Drive upload fails is retried every 10 minutes for one six-hour episode; expiry does not rearm for the same retained failure, while a genuinely new failed dump starts a fresh episode.

**Why:** immediate full dumps during application startup took nearly six minutes, pushed normal API requests into 30–289 second waits, and accumulated tens of gigabytes inside the project. A whole-file gzip PUT hit Cloudflare's 413 request-body limit. Subsequent real connector tests showed Cloudflare returns 403 Forbidden for *any* partial resumable PUT, even 290-byte gzip or raw bytes, while complete file PUTs succeed. Shrinking partial ranges cannot fix this transport.

**How to apply:** preserve upload-before-delete, complete size/checksum verification, the advisory lock, six-hour cadence, delayed first run, retry-until-lock-available behavior, and the bounded upload-recovery episode. Recovery retries only retained files and never creates extra dumps. Queue scheduled work that collides with recovery, but discard obsolete queued lock retries after success. When answering next-run questions, use the instance startup time rather than the last upload time, and treat pending retries as unconfirmed until a verified completion appears. In historical manifest tooling only, use full-range PUTs for bounded gzip objects, never partial-range proxy PUTs. Never treat orphan parts as complete; restore them only through a complete manifest and per-part plus whole-SQL hash verification. On failure, retain the source SQL.
