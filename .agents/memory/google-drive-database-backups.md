---
name: Google Drive database backups
description: Production backup destination, lifecycle, and scheduling rules that prevent database and project-storage contention.
---

Production database backups use `pg_dump --no-owner --no-privileges`, are named `S&PBACKUP-YYYY-MM-DD_HH-MM-SS.SQL`, and are stored uncompressed in the dedicated Google Drive backup folder indefinitely. Development servers do not run scheduled backups. Each production instance waits 10 minutes after startup, then attempts every 6 hours; a PostgreSQL advisory lock prevents simultaneous backups, and a locked-out attempt retries every 5 minutes until it runs. Each instance keeps at most one pending retry, so retries cannot fan out locally; concurrent instances may still produce an additional backup after the lock holder finishes. A complete SQL file whose Drive upload fails is retried every 10 minutes for one six-hour episode; expiry does not rearm for the same retained failure, while a genuinely new failed dump starts a fresh episode.

**Why:** immediate full dumps during application startup took nearly six minutes, pushed normal API requests into 30–289 second waits, and accumulated tens of gigabytes inside the project. A later whole-file gzip PUT hit Cloudflare's 413 request-body limit during live imports; compression alone does not bound request size.

**How to apply:** preserve upload-before-delete, exact remote-size verification, the advisory lock, six-hour cadence, delayed first run, retry-until-lock-available behavior, and the bounded upload-recovery episode. Recovery retries only retained files and never creates extra dumps. Queue scheduled work that collides with recovery, but discard obsolete queued lock retries after success. When answering next-run questions, use the instance startup time rather than the last upload time, and treat a pending retry as unconfirmed until an upload log appears. The connector WAF blocks raw SQL bodies and oversized compressed requests: gzip only bounded per-request HTTP transport chunks, with a generous margin below the gateway limit; Drive must decode them and store exact plain SQL bytes. Never prune Drive backups automatically. On failure, retain the source SQL.
