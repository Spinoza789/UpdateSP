Feature 2: Group-buy crypto refunds
Add a group-buy refund system that is enabled per group buy by an admin.
Admin configuration
In the backend group-buy settings, add an option such as:
Enable crypto refunds

Requirements:
* Refunds are disabled by default.
* Only authorized admins can enable or disable them.
* The setting must be persisted in the database.
* The group-buy order summary page must only show the refund option when refunds are enabled for that group buy.
* Disabling refunds must not delete historical refund records.
Customer refund request
When refunds are enabled, show an option on the group-buy order summary page:
I want a refund

When selected, display a form allowing the customer to:
* Enter their destination wallet address.
* Select the refund cryptocurrency and network.
* Initially support at least:
    * USDC ERC-20
    * USDT ERC-20
* Use the original payment asset and network wherever possible.
* Validate the wallet address and selected network server-side.
* Clearly explain that the refund is sent on-chain and cannot be reversed once submitted.
* Prevent duplicate active refund requests for the same order.
Only allow a refund request when:
* The order belongs to the authenticated customer.
* The order has a confirmed real crypto payment.
* The payment evidence is trustworthy and can be tied to the order.
* The order is not already refunded or cancelled.
* There is no active refund request.
* The requested asset and network are supported by the backend.
Do not infer refund eligibility from client-side transaction fields or USD totals.
Admin refund queue
Add a refund section to the backend/admin group-buy area showing refund requests that need processing.
The queue should show:
* Customer
* Order
* Group buy
* Requested asset
* Network
* Refund amount
* Destination wallet
* Request date
* Current status
* Any previous processing attempts
Allow an authorized admin or permitted group-buy organiser to:
* Review the request.
* Reject or retry it where supported.
* Submit the outgoing refund transaction ID/TXID.
* See clear validation and submission errors.
* Avoid processing refunds outside their permitted group-buy scope.
Refund processing
When the processor submits a TXID:
* Validate the TXID server-side.
* Verify the transaction independently on the correct blockchain/network.
* Confirm:
    * Correct asset
    * Correct network
    * Correct destination wallet
    * Exact refund amount
    * Successful execution
    * Required confirmation depth
* Do not trust the client-provided amount, USD value, exchange rate, or floating-point calculation.
* Use exact on-chain base-unit amounts.
* Do not support partial refunds unless explicitly added later.
* Do not support fiat, store-credit, or cross-network refunds.
* Do not handle private keys or automatically broadcast transactions.
Only after successful independent verification:
* Mark the refund as completed.
* Mark the associated order as refunded.
* Change the order status to Cancelled.
* Save the outgoing TXID.
* Show the TXID and blockchain explorer link to the customer.
* Record an audit trail.
If verification fails:
* Keep the order unchanged.
* Keep the refund request available for review or retry.
* Show a clear failure reason.
* Do not mark the order cancelled prematurely.
Refund states
Use explicit lifecycle states:
requested
verifying
verification_failed
completed

Active refund requests must prevent conflicting changes to:
* Order status
* Payment status
* Line items
* Shipping or delivery address
* Payment destination
* Order associations
* Other refund-sensitive order fields
Use transactions, idempotency checks, and appropriate locking so that concurrent admin actions cannot complete or cancel the same refund incorrectly.
Customer status display
On the customer order summary page, show the current refund state:
* Refund request submitted
* Refund is being verified
* Refund verification failed
* Refund completed
* Outgoing transaction ID
* Blockchain explorer link when available
* Clear explanation that completed crypto transactions cannot be reversed
Notifications
Use the application’s existing notification system to notify the customer when:
* A refund request is submitted.
* Refund processing begins, if supported.
* Verification fails.
* The refund is completed.
Do not create duplicate notifications when the same status update is retried.
Testing and verification
Add automated tests for:
* Admin enable/disable setting.
* Customer eligibility.
* Wallet and network validation.
* Duplicate request prevention.
* Unsupported asset/network rejection.
* Exact amount verification.
* Wrong recipient rejection.
* Wrong network rejection.
* Failed transaction rejection.
* Insufficient confirmation rejection.
* Successful completion and cancellation.
* Idempotent TXID submission.
* Concurrent processor attempts.
* Order mutation blocking while a refund is active.
* Organiser permission scoping.
* Customer visibility of the completed TXID and explorer link.
* Organiser payment confirmation marking only the organiser’s personal order as paid.
